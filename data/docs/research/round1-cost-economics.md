# 03. 비용은 어디서 나오나 — 캐시 읽기의 지배

다섯 케이스 모두 최대 비용원은 output 토큰이 아니라 **cache read**였다. 에이전트가 도구를 호출할 때마다 누적된 컨텍스트 전체를 캐시에서 다시 읽는데(호출당 수십만~수백만 토큰), API 호출이 많고 컨텍스트가 긴 에이전트일수록 이 비용이 기하급수로 쌓인다. case1의 단독 에이전트는 148회 API 호출 동안 1,626만 캐시 읽기 토큰을 소비했다 — **전체 비용의 74%**다.

## 케이스별 비용 구성

| 케이스 | 순수 개발 비용 |
|---|---|
| case1 | $10.95 |
| case2 | $8.72 |
| case3_1 | $7.37 |
| case2_1 | $5.83 |
| case3 | $5.03 |

비용 구성요소는 output(생성) · cache read(컨텍스트 재읽기) · cache write(캐시 기록) 세 가지이며, uncached input은 케이스당 $0.001 미만이라 무시할 수 있는 수준이다.

## 케이스별 API 호출·토큰 상세

| 케이스 | API 호출 | 도구 호출 | output 토큰 | cache read 토큰 | 호출당 평균 컨텍스트 |
|---|---|---|---|---|---|
| case1 | 148 | 158 | 72,881 | 16.26M | 110k |
| case2 | 148 | 157 | 98,816 | 18.81M | 127k |
| case2_1 | 88 | 90 | 62,302 | 7.43M | 84k |
| case3 | 110 | 118 | 72,660 | 8.25M | 75k |
| case3_1 | 90 | 94 | 105,515 | 7.04M | 78k |

## 왜 분업이 싼가

단일 에이전트(case1, case2의 개발자)는 설계부터 검증까지 전 과정의 컨텍스트를 한 세션에 끌고 다니며 140회 이상 호출을 반복한다. 반면 역할을 쪼개면 각 에이전트의 컨텍스트가 짧아지고 호출 수도 줄어, cache read가 절반 이하로 떨어진다.

> **토큰 효율의 지배 변수는 "모델 단가"가 아니라 "에이전트당 컨텍스트 길이 × 호출 횟수"였다.**

## 파이프라인 타임라인

세그먼트는 단계별 소요 시간(FE/BE 병렬 구간은 더 오래 걸린 쪽 기준)이며, Opus5/Sonnet5 담당 단계가 구분되어 표기된다.

| 케이스 | 시간 | 점수 |
|---|---|---|
| case3_1 | 19.6분 | 100점 |
| case2_1 | 19.8분 | 100점 |
| case3 | 19.9분* | 98점 |
| case1 | 27.0분 | 100점 |
| case2 | 27.2분 | 100점 |

이 문서의 핵심 결론(컨텍스트 길이 × 호출 횟수가 비용의 지배 변수)은 `classify_complexity`와 `compare_pipelines` 도구가 파이프라인을 추천할 때 근거로 인용해야 하는 가장 중요한 원칙 중 하나다.
