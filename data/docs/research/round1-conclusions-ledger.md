# 07. 결론 — 제한된 토큰으로 개발하는 법

1. **최상위 모델에게 전부 맡기는 것이 가장 비쌌다.** case1(Opus 단독)은 품질에서 아무 우위 없이 최고 효율 대비 2.18배의 비용을 냈다. 단일 에이전트가 전 과정의 컨텍스트를 끌고 다니는 구조 자체가 cache read를 폭증시킨다.
2. **비용의 지배 변수는 모델 단가가 아니라 컨텍스트 길이 × 호출 횟수다.** Opus를 개발자로 쓴 case2_1($5.83)이 Sonnet을 개발자로 쓴 case2($8.72)보다 쌌다 — Opus가 절반의 API 호출로 일을 끝냈기 때문이다. "싼 모델 = 싼 파이프라인"이 아니다.
3. **설계 문서는 비용 배분 장치다.** Opus의 상세 설계(1,480~1,988줄)는 Sonnet 개발자를 100점으로 이끌었고(case2, case3), Sonnet의 얇은 설계(778~915줄)는 Opus 개발자의 역량이 메웠다(case2_1, case3_1). 어느 쪽이든 품질은 지켜졌지만, "비싼 모델의 지능을 어느 단계에 투입하느냐"에 따라 총비용이 달라진다.
4. **권장 파이프라인 두 가지.** 토큰 최우선이면 case3(Opus 설계 → Sonnet FE/BE 분업, 100점 환산 $5.13) — 단, 병렬 조율·인프라 재시도 리스크와 코드 위생 감점(mock 잔재 −2)이 이 구조에서 나왔음을 감수해야 한다. 운영 단순성까지 고려하면 case2_1(Sonnet 설계 → Opus 단독 개발, $5.83, 100점) — 에이전트 2개, 조율 리스크 없음, 최단급 시간(19.8분). 둘의 효율 차이는 12%에 불과해, 실무에서는 case2_1이 더 안전한 기본값이다.
5. **병렬 FE/BE 분업의 실익은 비용이 아니라 시간이다.** 분업 자체의 비용 이득은 컨텍스트 축소에서 오지만, 문서 계약만으로 병렬 구현한 결합부에서 결함 0건이라는 결과는 "완결된 API 계약 문서"가 전제였다. 계약이 부실하면 이 구조는 가장 먼저 무너진다. 또한 이번 실험에서 코드 위생 지적(도달 불가능한 mock 잔재, UI 블록 중복 시비)은 모두 병렬 분업 케이스에서만 나왔다 — 서버 없이 개발하는 FE의 작업 방식이 남기는 흔적이다.
6. **오케스트레이션 안정성이 모델 선택만큼 중요하다.** 이번 실험에서 재실행 오버헤드($22.21)는 순수 개발 비용의 59%였다. 재시도 정책, resume 캐시 의미론, 자원 한도 대응이 없으면 파이프라인 최적화로 아낀 토큰을 운영 사고로 다시 태운다.
7. **한계.** 케이스당 1회 실행(n=1), 품질 천장 효과, 단일 과제 도메인. 순위의 재현성을 주장하려면 반복 실행과 난이도 상향이 필요하다.
