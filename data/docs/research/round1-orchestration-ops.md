# 05. 에이전트 지시 체계 — 누가 누구에게 무엇을 하달했나

오케스트레이터(Claude Fable 5)가 워크플로우 엔진으로 각 에이전트를 생성하고, 역할별 프롬프트로 지시를 하달했다. 에이전트 간 직접 통신은 없다 — 설계자가 디스크에 남긴 PLAN.md/DESIGN.md가 유일한 핸드오프 채널이며, 개발자는 그 문서와 PRD만 보고 구현한다. 모든 에이전트는 structured output(JSON 스키마 강제)으로 자가 보고를 반환했다.

## 공통 지시 규칙 (모든 에이전트)

- 자기 케이스 디렉토리 밖 접근 금지(PRD 읽기만 예외) — 케이스 간·평가 자료 오염 차단
- npm/외부 패키지 금지, 시작한 서버 프로세스는 종료 후 반환, 케이스별 고유 포트로 자가 테스트
- 설계자: 구현 코드 작성 금지, 문서만 산출 / 개발자: 설계 문서가 PRD와 충돌하면 PRD 우선
- FE/BE 병렬: BE는 `public/` 접근 금지, FE는 `public/` 밖 쓰기 금지 — "서로 대화 없이 계약만 보고 구현"

## 케이스별 지시·자가보고 요약

**case1 — 하네스 엔지니어링** (에이전트 1개 · $10.95 · 27.0분)
지시 요지: "솔로 풀스택 엔지니어로서 전권을 갖는다. 간단한 PLAN/DESIGN을 먼저 쓰고 전체 앱을 구현한 뒤 엔드투엔드 검증하라." 자가 보고: 119개 어설션 HTTP 테스트 스위트 자체 작성·전부 통과. 검증 중 실제 버그 3건 발견·수정(413 응답 전 소켓 파괴, 잘못된 percent-encoding 500 오류, 모바일 레이아웃 붕괴). 산출: 문서 209줄 + 코드 2,398줄 / 18파일 — 문서는 최소, 검증은 최다.

**case2 — 설계 가중 (Opus 설계 → Sonnet 개발)** (에이전트 2개 · $8.72 · 27.2분)
설계자 지시: "단일 풀스택 엔지니어가 네 문서만 보고 구현한다. 모든 엔드포인트의 요청/응답/에러코드까지 완결된 명세를 써라." 설계자 자가 보고: PLAN 375줄 + DESIGN 1,613줄, FR/NFR 전 항목 3회 이상 교차 참조된 추적성 테이블 포함. PRD가 침묵한 7개 지점의 결정(D-1~D-7: 자동 로그인, 대소문자 무시 유니크, 역방향 요청 409 등)을 문서화하고, 구현 함정 2개(scrypt await 후 유니크 재검사, URL 디코딩 후 경로 격리)를 개발자에게 명시적으로 경고. 개발자 자가 보고: 설계 문서의 지시 구조(lib/ 11모듈 + services/ 5 + routes/ 5)를 그대로 구현, 28파일 생성. 원시 소켓 10MB 테스트로 413 생존 검증까지 수행.

**case2_1 — 개발 가중 (Sonnet 설계 → Opus 개발)** (에이전트 2개 · $5.83 · 19.8분)
설계자 자가 보고: PLAN+DESIGN 915줄(case2의 절반 이하 분량). 256비트 세션 토큰, 쿠키+Bearer 이중 전송, 열거 방지 로그인 에러, 1MB 바디 캡, 파일별 쓰기 큐 등 핵심 결정을 명시. 개발자: 21파일 생성. 얇은 설계를 받았지만 Opus의 자체 판단으로 빈틈을 메워 100점 구현 — **개발 모델의 역량이 설계 문서의 부족을 보완한 사례**. 가장 적은 output 토큰(62.3k)과 API 호출(88회)로 최단급 시간 달성.

**case3 — FE/BE 분업, 설계 가중 (Opus 설계 → Sonnet×2 병렬)** (에이전트 3개 · $5.03 · 19.9분* · 최고 효율)
설계자 지시: "FE/BE 엔지니어 둘이 서로 대화 없이 병렬 구현한다. 둘이 맹목적으로 구현해도 맞물리도록 API 계약과 파일 소유권 경계를 완결하라." PLAN+DESIGN 1,480줄 + API 계약 + 업무 분장. BE 자가 보고: 1차 시도가 API 연결 끊김으로 중단(운영 사건 #2) → 재시도 에이전트가 이전 산출물(lib/ 6파일)을 이어받아 12파일 완성, 인증·인가·친구 전 플로우 자가 검증. FE 자가 보고: 서버 없이 계약 문서만으로 6페이지+8모듈 구현, 계약 대비 코드 리뷰로 검증 — 평가에서 결합부 결함 0건. **감사 조정 −2**: FE가 서버 없이 개발하며 사용한 mock 스캐폴드(25줄, USE_MOCK=false로 봉인)를 삭제하지 않고 남김 — 병렬 분업 방식의 흔적이 그대로 데드 코드 감점으로 이어진 사례.

**case3_1 — FE/BE 분업, 개발 가중 (Sonnet 설계 → Opus×2 병렬)** (에이전트 3개 · $7.37 · 19.6분)
설계자: PLAN+DESIGN 778줄. BE 자가 보고: 145개 API 계약 검증 + 17개 재시작 영속성 검증 + 16개 신규 부팅 검증 = 178체크. 포트 충돌 시 zombie 프로세스가 남는 결함을 스스로 발견·수정. FE: 가장 많은 output(66.2k)으로 16개 파일의 풍부한 UI 구현. 1차 평가자는 버튼 UI 블록 중복 약 16줄에 −2를 줬으나, 재실행 평가자와 감사는 통과 판정 — 최종 100점(평가자 변동성 사례). 얇은 설계(778줄)에서 Opus 개발자들이 세부를 각자 결정 — 품질은 지켰지만 output 토큰이 가장 많음(105.5k).

# 06. 운영 사건 로그 — 벤치마크가 드러낸 오케스트레이션의 현실

계획대로면 24개 프로세스로 끝났을 실험이 실제로는 29회의 에이전트 실행을 소모했다. 재실행 오버헤드 합계 $22.21 — 순수 개발 비용의 59%에 달한다.

## 사건 #1 — 파이프라인 null 드롭 (case1이 실행되지 않음)

워크플로우 1단계에서 설계 단계가 없는 case1에 null을 반환하자, 엔진이 "아이템 탈락"으로 해석해 2단계(개발)를 통째로 스킵. 11개 계획 중 10개만 실행됐다.
**교훈**: 파이프라인 스테이지의 null 반환은 탈락 신호다. 스킵 의도라면 sentinel 객체를 반환하라.

## 사건 #2 — 인프라 오류 (case3 백엔드 에이전트 중단)

"API Error: Connection closed mid-response" — 모델 문제가 아닌 API 연결 끊김으로 Sonnet BE 에이전트가 server.js 작성 전에 사망. 재시도 에이전트가 이전 산출물을 이어받아 완성했다. 실패 시도 비용 $0.58은 case3 실비용에 포함하되 별도 표기.
**교훈**: 장시간 에이전트 실행에는 인프라 수준의 재시도 경로가 반드시 필요하다.

## 사건 #3 — 프리픽스 캐시 무효화 (완료된 에이전트 6개 재실행)

사건 1·2 복구를 위해 스크립트를 수정해 재개하자, resume 캐시가 "호출 순서 프리픽스" 기준이라 새 호출이 앞에 삽입되면서 이미 완료된 개발 에이전트들까지 재실행됐다. 재실행분은 기존 산출물을 발견하고 재검증만 수행(코드 변경 0~1건)했지만 $21.63의 토큰을 태웠다. 산출물 오염은 없음(동일 모델·동일 설계 기반)을 확인.
**교훈**: 워크플로우 resume은 content-key가 아니라 호출 순서 캐시다. 재개용 수정은 반드시 기존 호출 순서의 뒤에 추가돼야 한다.

## 사건 #4 — 세션 토큰 한도 (평가 단계 중단·재개)

평가 워크플로우 도중 세션 한도 도달로 6개 중 3개(평가자 2 + 감사)가 실패. 상태 파일(RESUME.md)에 재개 절차를 기록하고 중단, 한도 리셋 후 동일 runId로 재개해 완료했다.
**교훈**: 장기 벤치마크는 중단 가능 지점마다 재개 상태를 디스크에 남겨야 한다. 자원 한도는 실험 설계의 일부다.

## 사건 #5 — 평가 재개 시에도 프리픽스 재실행 재발

사건 3과 동일 기전: 첫 실패 지점(eval:case2) 이후 순서의 완료된 평가자 2개가 재개 시 다시 실행됐다. 부수 효과로 평가자 변동성이 드러났다 — case3_1은 1차 평가 98점, 재실행 평가 100점으로 같은 산출물에 다른 판정이 나왔고, 감사가 루브릭 원문 기준으로 최종 확정했다.
**교훈**: 병렬 fan-out 내부의 부분 실패는 프리픽스 캐시와 상성이 나쁘다. 그리고 LLM 평가는 반드시 감사 단계로 이중화하라 — 단일 평가자의 판정은 ±2점 흔들린다.

## 비용 버킷 정산

| 비용 버킷 | 금액 | 내용 |
|---|---|---|
| 순수 개발 (벤치마크 지표) | $37.89 | 5개 케이스의 설계+개발 생산적 실행 17회 중 12회분 |
| 인프라 재시도 | $0.58 | 사건 2 — case3 BE 실패 시도 |
| 불필요 재실행 (사건 3) | $21.63 | 프리픽스 캐시 무효화로 인한 재검증 5회 |
| **실제 총 개발 지출** | **$60.10** | 위 합계 (평가·루브릭·오케스트레이터 비용 별도) |

프로세스 예산: 할당 25개 중 논리적 프로세스 18개(개발 11 + 재시도 1 + 루브릭 1 + 평가 5 + 감사 1 중 고유 역할 기준) 사용. 실패·캐시 재실행을 포함한 물리적 실행 횟수는 29회.

> 이 문서는 `commit_pipeline`의 원자성 보장 로직(G3)의 실제 근거다 — 재실행·인프라 실패는 반드시 발생하며, 원자성 보장 없이는 예산 측정이 오염된다는 것이 이 벤치마크 전체의 반복되는 교훈이다.
