# 13. 운영 사건 및 정산 방법론

라운드 2도 실측 벤치마크답게 네 건의 운영 사건을 겪었다. 핵심 원칙은 R1과 동일 — 중단이 없었다면 발생하지 않았을 토큰은 순수 개발(productive) 지표에서 제외하고 낭비 버킷으로 분리 정산한다.

## 사건 #1 — 세션 토큰 한도 → 개발/평가 에이전트 중단 + 클린 재실행

개발 워크플로우 8개 에이전트 중 5개 완료 시점에 세션 사용량 한도 도달. 실패 3건: dev:case3:be(Sonnet), dev:case2_1:fullstack(Opus), dev:case3_1:be(Opus). 봉인 평가 키트도 같은 원인으로 종료(디스크 산출물 없음).

**클린 재실행 방법론**: 실패 case3 BE의 잔류 서버(포트 3201) kill 후, 실패 3개 에이전트의 부분 산출물을 전부 삭제했다 — 재실행 에이전트가 부분 작업의 이득을 보면 토큰 측정이 오염되기 때문. 이후 캐시 재개(resumeFromRunId): 완료 5건은 캐시 재생(토큰 0), 실패 3건만 클린 라이브 재실행.
**교훈**: 부분 산출물을 남긴 재실행은 토큰 측정을 오염시킨다. 벤치마크 재실행은 반드시 클린 상태에서.

## 사건 #2 — 트랜스크립트 usage 과소기록 → 출력 토큰 재구성

assistant 메시지 usage가 일부 메시지에서 최종값 대신 초기 스냅샷(output 2~5토큰)만 기록됐다. 예: case2_1 설계 에이전트가 72KB 문서 2개를 썼는데 기록 출력 합계는 978토큰. 입력측(input/cacheCreate/cacheRead)은 요청 시점 확정값이라 신뢰 가능.
**보정**: 메시지별 `effective_output = max(기록값, 생성 콘텐츠 바이트 ÷ 3.8)`(생성 콘텐츠 = text + thinking + tool_use JSON, 중복 블록 dedupe). 12개 에이전트 전원 보정 발생 — 기록값 227k → 재구성 640k 출력 토큰.
**교훈**: R1 정산은 기록값 기준이다. 이 재구성은 라운드 내 케이스 비교엔 동일 적용되어 유효하나, 라운드 간 절대 비교에는 캐비앗이 있다(§14 참고).

## 사건 #3 — case3_1 FE 불필요 재실행 (rerun_waste)

재개 시 case3_1/fe는 1차에서 완주했음에도 캐시 프리픽스 미적중으로 재실행됐다(병렬 이슈 순서로 인한 prefix 불일치 추정). 재실행분은 완성된 public/을 보고 검증만 수행(재구성 출력 ~3.1k), 파일 무변경(mtime 전부 1차 시각). 1차 완주분은 productive, 재실행분은 rerun_waste.
**교훈**: R1 사건 3과 동일 범주 — 워크플로우 resume은 content-key가 아니라 호출 순서 프리픽스 캐시다.

## 사건 #4 — 하니스 프로브 결함 4건 수정 후 재채점

1차 자동 채점은 case3 82.17 · case2_1 82.17 · case3_1 83.17(/86)로 세 케이스의 감점 패턴이 완전히 동일했다 → 구현이 아니라 프로브를 의심. 진단 결과 4항목 모두 하니스 측 문제로 확정: IN-04(프로브 코드 버그로 예외가 0점 처리), F-24(재시드 stale workspaceId 오판정), PF-05(400 VALIDATION도 PRD상 타당한데 200-캡핑만 인정), RT-06(hello 뒤 위치 무관 sync.required도 인정하도록 교정). 수정 원칙: 루브릭 배점·항목 불변, 프로브의 PRD 해석만 교정, 3케이스 동일 적용. 재채점 결과 3케이스 모두 86/86.
**교훈**: 전 대상에 동일한 감점 패턴은 대상이 아니라 측정 도구를 먼저 의심하라. 단, 배점·항목은 손대지 않고 해석만 교정한다.

# 14. 모델·정산 캐비앗

R2의 'opus' 별칭은 claude-opus-4-8(단가는 opus-5와 동일 $5/$25), 'sonnet'은 claude-sonnet-5. 자동 채점은 봉인 하니스(개발과 격리, 소스 미열람, 셀프테스트 스텁 19.5/86)로, 나머지 14점은 LLM 판정 + 감사(조정 0건)로 산출했다. R2 출력 토큰은 usage 과소기록 보정(재구성)값이다 — 라운드 간 절대 비교는 이 재구성 방법론 차이를 감안해야 한다.

# 15. 라운드 간 비교 — $/점의 완전 역전

같은 세 조합을 간단 과제(R1)와 복잡 과제(R2)에 각각 투입한 결과, $/점 순위가 뒤집혔다. R1의 최고 효율(case3)이 R2에서 최악이 됐고, R1 2위(case2_1)가 R2 1위로 올라섰다.

| 케이스 | 구성 | R1 $/점 (순위) | R2 $/점 (순위) | 변화 |
|---|---|---|---|---|
| case3 | Opus설계→Sonnet FE/BE | $0.0513 (1위) | $0.1123 (3위) | 1→3위 · +119% |
| case2_1 | Sonnet설계→Opus풀스택 | $0.0583 (2위) | $0.0658 (1위) | 2→1위 · +13% |
| case3_1 | Sonnet설계→Opus FE/BE | $0.0737 (3위) | $0.0910 (2위) | 3→2위 · +23% |

## 해석 — 복잡도가 최적 배치를 뒤집는다

간단 과제(R1)에선 "비싼 모델은 설계에, 싼 모델은 개발에"(case3: Opus 설계 → Sonnet 개발)가 이겼다. 설계만 잘 잡히면 쉬운 구현은 싼 모델로 충분했기 때문이다. 복잡 과제(R2)에선 이 전략이 최악이 됐다. Sonnet 개발자가 규범을 맞추느라 시행착오를 반복(출력 87k·캐시리드 23.6M, 타 케이스의 ~3배)했고, 그 재읽기 비용이 단가 이점을 압도했다. 대신 Sonnet 설계 → Opus 풀스택(case2_1)이 1위 — "설계는 싼 모델로도 충분, 개발엔 강한 모델"이 우세해졌다. 얇은 설계라도 강한 개발 모델이 빈틈을 메운다.

## 분해는 약한 모델에 보약, 강한 모델에 세금

같은 Sonnet 설계 → Opus 개발 조합에서 풀스택(2 에이전트, case2_1)과 FE/BE 분리(3 에이전트, case3_1)를 비교하면 두 라운드 모두 풀스택이 저렴했다 — 즉 강한 개발 모델(Opus)에겐 분리가 세금이다. 그러나 이는 개발자가 강할 때의 이야기이고, 약한 모델(Sonnet)이 개발하면 정반대다: R1에서 Opus 설계 → Sonnet 풀스택(case2 $8.72)보다 FE/BE 분리(case3 $5.03)가 오히려 쌌다 — 약한 모델에겐 분리가 보약. **분해의 손익은 라운드가 아니라 개발 모델의 강도로 갈린다.**

| Sonnet설계→Opus개발 | R1 $/점 | R2 $/점 |
|---|---|---|
| 풀스택 · 2 에이전트 (case2_1) | $0.0583 | $0.0658 |
| FE/BE 분리 · 3 에이전트 (case3_1) | $0.0737 | $0.0910 |

단, 분리에는 완결된 API 계약 문서가 전제이고 조율 리스크(인프라 재시도·mock 잔재 감점)가 따른다 — 약한 모델에서 얻는 비용 이득과 맞바꾸는 대가다.

# 16. 최종 결론 — 제한된 토큰으로 가장 효과적인 AI 개발법 (2라운드 종합)

1. **최적 조합은 과제 복잡도에 따라 달라진다.** 간단 과제(R1)에선 Opus 설계 → Sonnet 개발(case3, $0.0513/점)이 최고 효율이었지만, 복잡 과제(R2)에선 정반대로 Sonnet 설계 → Opus 풀스택(case2_1, $0.0658/점)이 최고였다. "정답 파이프라인"을 고정하지 말고 난이도로 선택하라.
2. **복잡 과제의 권장값: Sonnet 설계 → Opus 풀스택 (에이전트 2개).** 최저 $/점($0.0658), 최단 시간(26.9분), 98.33점. 설계는 싼 모델로도 충분했고(얇은 설계라도 강한 개발 모델이 메움), 지능은 개발 단계에 투입하는 편이 복잡도에 강했다.
3. **비용의 지배 변수는 모델 단가가 아니라 컨텍스트 길이 × 호출 횟수(cache read)다.** 두 라운드 공통. 정가가 더 싼 Sonnet을 개발자로 써도, 복잡 과제에서 시행착오로 캐시 재읽기가 3배(23.6M)로 불면 총비용은 더 비싸진다. "싼 모델 = 싼 파이프라인"은 성립하지 않는다.
4. **분해(FE/BE 분리)의 손익은 개발 모델 강도로 갈린다** — 약한 모델엔 보약, 강한 모델엔 세금. 강한 개발 모델(Opus)에선 3-에이전트 분리(case3_1)가 2-에이전트 풀스택(case2_1)보다 두 라운드 모두 비쌌다(세금). 반대로 약한 개발 모델(Sonnet)에선 R1에서 분리(case3 $5.03)가 풀스택(case2 $8.72)보다 쌌다(보약). 강한 모델엔 풀스택으로 컨텍스트를 몰아주고, 약한 모델일 때만 쪼개라 — 어느 쪽이든 완결된 API 계약이 전제이고 조율 리스크가 따른다.
5. **품질은 여전히 변별하지 못했다** — 더 어려워졌는데도. 복잡 과제에서도 세 구현이 자동 86/86 만점, 총점 98.33~99.0. 두 최신 모델의 역량이 이 난이도까지는 상한을 유지했다. 변별은 비용·시간과 LLM 판정 14점의 소수 차이에 남았다.
6. **오케스트레이션 안정성이 모델 선택만큼 중요하다.** R2 실지출의 34%($13.93/$40.52)가 세션 한도·재실행 낭비였다. 클린 재실행 규율, resume 프리픽스 캐시 이해, 자원 한도 대응이 없으면 파이프라인으로 아낀 토큰을 운영 사고로 다시 태운다.
7. **한계.** 케이스당 n=1, R2는 상위 3개 조합만, 라운드 간 강모델 정체성(opus-4-8 vs opus-5)과 출력 재구성 방법론 차이. 순위 재현성을 주장하려면 반복 실행과 난이도 3단계 이상 스윕이 필요하다.

> **두 라운드 최종 답**: 토큰 효율을 좌우하는 건 "가장 비싼 모델을 쓰느냐"가 아니라 "강한 모델의 지능을 어느 단계에 투입하느냐, 그리고 에이전트당 컨텍스트를 얼마나 짧게 유지하느냐"다. 간단 과제라면 설계에, 복잡 과제라면 개발에 강한 모델을 두고, 에이전트 수는 필요 최소로 — 복잡 실무 기준 Sonnet 설계 → Opus 풀스택(에이전트 2개)이 이번 벤치마크의 최선값이다.
