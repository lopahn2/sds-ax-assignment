# 라운드 4 — 복잡도 라우터: 지도를 자동 내비게이션으로

R1~R3은 "과제 복잡도 → 최적 파이프라인"의 지도를 손으로 그렸다. R4는 그 지도를 자동 내비게이션으로 바꾼다 — 스펙을 읽고 W-SIMPLE / W-COMPLEX를 스스로 고르는 6축 루브릭 라우터를 저렴한 모델로 세우고, 84판정으로 검증했다. 이어 그동안 미측정으로 남았던 셀(all-Sonnet)을 실측해 카탈로그를 확정하고, 루브릭의 복잡도 임계(≥2축)가 경제적으로 옳은지 경계 과제로 직접 시험했다.

## 20. 라우터 실험 — 6축 루브릭과 84판정

세 라운드의 결론은 한 문장으로 압축된다 — "간단하면 싼 모델, 복잡하면 강한 모델, 강한 모델엔 풀스택." 하지만 실무에서 이 규칙을 쓰려면 먼저 "이 과제는 간단한가 복잡한가"를 판정해야 한다. R4는 이 판정 자체를 저렴한 모델의 라우터에게 맡길 수 있는지 묻는다.

### 6축 루브릭 — "싼 모델이 시행착오를 폭증시키는 원인" 목록 ★가장 중요한 판정 기준★

루브릭의 6축은 R1~R3 실측에서 저렴한 개발 모델이 자가 반복(시행착오)을 폭증시킨 원인을 추출한 것이다. 각 축은 참/거짓으로 판정한다.

| 축 | 질문 | 해당 판정 기준 |
|---|---|---|
| A1 동시성·경합 | 병렬 요청이 같은 상태를 두고 경쟁하는가? | 낙관적 잠금·버전 충돌·재고/좌석 경합·정확히-하나-성공 요구가 명시됨 |
| A2 시간적 순서 | 이벤트 순서·리플레이·수렴을 보장해야 하는가? | 실시간 동기화(SSE/WS)·이벤트 순번·재접속 복구·다중 클라이언트 일관성 |
| A3 장애 불변식 | 크래시/재시작 후 지켜야 할 불변식이 명시되는가? | 원자적 쓰기·복구·데이터 무결성 조건(단순 "저장된다"는 제외) |
| A4 수치 성능 목표 | p95·처리량 같은 정량 목표가 있는가? | 구체적 숫자 목표 + 대량 데이터 조건 |
| A5 권한 조합 폭발 | 역할×리소스 매트릭스가 20셀 이상인가? | 역할 3개 이상 × 행위별 상이한 규칙 |
| A6 검증 방식 | 순차 curl로 전 요구사항 검증 가능한가? | 다중 클라이언트·동시 요청·시간 조건 프로브가 필요하면 해당 |

### 결정 규칙과 비대칭 편향 — "불확실 시 COMPLEX로 기울여라" ★가장 중요한 규칙★

**해당 축 ≥ 2 → COMPLEX**(W-COMPLEX: Sonnet 설계 → Opus 풀스택), **≤ 1 → SIMPLE**(W-SIMPLE: 저비용 설계 → Sonnet FE/BE 분리).

핵심은 애매하면 COMPLEX로 세라는 편향 규칙이다. 근거는 R1~R3 실측 오분류 비용의 비대칭이다 — 복잡 과제를 W-SIMPLE로 잘못 보내면 +72%(R2 case3 $11.12) 손해, 간단 과제를 W-COMPLEX로 보내면 +16%(R1 case2_1 $5.83)에 그친다. **틀릴 거라면 비싼 쪽(COMPLEX)으로 틀리는 편이 4배 이상 싸다.** 출력은 6축 불리언 + hit_count + 분류 + confidence + 한 문장 근거의 JSON.

### 벤치 설계 — 14과제, 생성·라벨·라우터 3자 격리

벤치는 실제 PRD 2개(R1 todo = SIMPLE 정답, R2 TeamBoard = COMPLEX 정답)와 신규 미니 PRD 12개(simple 4 / complex 4 / 경계 4)로 구성했다. 공정성을 위해 세 역할을 상호 격리했다 — 미니 PRD를 짓는 생성자, 정답 라벨을 매기는 라벨러, 판정하는 라우터가 서로의 산출을 보지 못한다. 두 라우터 모델(Haiku 4.5 vs Sonnet(low))이 각 과제를 3회 반복 판정 → 14 × 3 × 2 = 84판정. 포트폴리오의 6/14(≈43%)가 SIMPLE 정답이다.

### 라우터 모델 비교

| 라우터 모델 | 전체 정확도 | 경계 정확도 | 판정당 비용 | 유일/최다 오분류 방향 |
|---|---|---|---|---|
| **Haiku 4.5 (채택)** | 41/42 (97.6%) | 12/12 (100%) | $0.0131 | SIMPLE→COMPLEX 1건 (안전) |
| Sonnet(low) | 40/42 (95.2%) | 10/12 (83%) | $0.0273 | COMPLEX→SIMPLE 2건 (위험) |

각 모델 42판정 = 14과제 × 3반복. 경계 = 미니 경계 4과제 × 3반복 = 12. 안정성: 각 모델 1과제만 반복 간 불일치(Haiku=T03, Sonnet=T12) — 기준 ≤1/14 충족. 명백 과제 10개는 양 모델 3반복 만장일치.

### ★ H3 확증 — 오분류의 방향까지 비대칭이었다

정확도보다 중요한 발견은 틀리는 방향이다. Haiku의 유일한 오분류는 SIMPLE→COMPLEX(T03) — 안전한 쪽(+16% 손해)이며, 편향 규칙이 의도대로 작동했다. 반면 Sonnet(low)의 오분류 2건(T12)은 모두 COMPLEX→SIMPLE — 위험한 쪽(+72% 손해)으로, 애매한 경계에서 편향 규칙을 적용하지 못했다. 비용가중 결과(오라클=1.0)로 환산하면 Haiku 1.0038 vs Sonnet 1.0342 — **Haiku는 틀려도 거의 공짜로 틀린다.**

**모델 선택 결론: 라우터는 Haiku다** — 더 싸고($0.013 vs $0.027), 더 정확하고, 틀릴 때 안전한 방향으로 틀린다.

### T09 축 상관성 발견 — 실시간(A2)은 검증 방식(A6)을 동반한다

경계 과제 T09(todo + SSE)에서 교차 판정이 갈렸다. 생성자는 "실시간 하나만 얹은 1축 과제"로 의도했지만, 라벨러는 A2(시간적 순서) + A6(검증 방식) = 2축으로 매겼다. 루브릭 조문상 라벨러가 옳다 — 실시간 동기화 요구(A2)는 순차 curl로 검증 불가능하므로 다중 클라이언트 프로브(A6)를 사실상 강제한다. 즉 **SSE 하나만 있어도 자동으로 2축이 되어 COMPLEX로 분류된다.** 이 축 상관성은 §21의 경계 실측에서 경제적으로도 옳음이 확인된다.

## 21. 카탈로그 갱신 & 경계 실측

### 옵션 A — 미측정 셀 실측: all-Sonnet이 새 W-SIMPLE

R1 과제(소셜 Todo)를 Sonnet 설계 → Sonnet FE/BE 분리 파이프라인으로 실측했다. 결과는 R1 루브릭 전 항목 통과 **100/100** · **$3.12**(프로모션 인트로가 $2.08). R1 우승자였던 case3(Opus 설계 → Sonnet 분업, $5.03/98점) 대비 **−38%**, $/점 $0.0312. 설계 모델 무관성 가설(간단 과제에선 설계에 Opus를 쓸 필요가 없다)이 실측으로 확증됐다.

**갱신된 카탈로그**: W-SIMPLE $3.12(all-Sonnet) · W-COMPLEX $6.47(Sonnet설계+Opus풀스택, R2 case2_1 실측). 간단 과제에서 강한 모델은 설계 단계에서도 이득이 없다 — 오히려 단가만 얹힌다.

### 4정책 포트폴리오 총비용 비교 (42판정 가중, 갱신 카탈로그 기준)

| 정책 | 총비용 |
|---|---|
| 오라클(완벽 배분, 상한) | $211.4 |
| **라우터(Haiku, 채택)** | **$214.2** |
| 항상-COMPLEX(보수적 고정) | $260.2 |
| 항상-SIMPLE(공격적 고정) | $323.0 |

라우터는 오라클 대비 **+1.3%**(달성가능 절감의 94.4% 포착) · 항상-COMPLEX 대비 **−17.7%** · 항상-SIMPLE 대비 **−33.7%**.

### 오분류 비용표 (갱신 카탈로그 기준)

간단→W-COMPLEX 오배정은 +87%($2.71), 복잡→W-SIMPLE 오배정은 +72%($4.65, R2 case3 proxy). 비율로는 간단→COMPLEX가 더 커 보이지만, **절대액으로는 여전히 복잡→SIMPLE($4.65)이 간단→COMPLEX($2.71)보다 아프다.** 결론: "불확실 시 COMPLEX" 편향 규칙은 유지하되, 격차가 좁혀진 만큼 향후 완화 여지는 있다.

### 옵션 B — 경계 실측: 루브릭 임계(≥2축)는 경제적으로 옳은가

갱신된 W-SIMPLE(all-Sonnet)이 저렴해졌으니, 경계 과제 T09(todo + SSE, 라벨러 판정 2축)를 양 파이프라인 모두로 엔드투엔드 실측했다.

| 파이프라인 | 비용(정가) | 품질 | 비고 |
|---|---|---|---|
| W-COMPLEX (Sonnet설계+Opus풀스택, 라우터 선택) | $4.30 | 30/30 | 강한 개발 모델이 실시간 축 반복을 억제 |
| W-SIMPLE (all-Sonnet) | $4.83 | 30/30 | Sonnet BE가 SSE에서 시행착오 폭증 |

품질은 사전 작성한 30프로브 체크리스트로 두 구현을 개별(fresh DATA_DIR·전용 포트) 평가했고 실시간 축은 실제 스트리밍 SSE 클라이언트(2-클라이언트 순서 동일성·Last-Event-ID 정확 재전송·재동기화)로 검증. 양군 30/30 동등.

**★ 판정**: 정가 기준 W-COMPLEX $4.30 < W-SIMPLE $4.83 — 강한 개발 모델(Opus)이 11% 저렴했다. 품질이 동등한 상태에서 비용까지 W-COMPLEX가 이겼으니, **라우터·라벨러의 T09=COMPLEX 분류가 비용상 정답**이다. 시행착오 시그니처 재현: W-SIMPLE의 Sonnet BE가 입력측 8.24M 토큰·도구 75회를 태웠다 — W-COMPLEX Opus 전체(2.78M)의 3배.

### 캐비앗 — 임계는 단가비의 함수다

이 판정은 정가($5/$25 · $3/$15) 기준이다. **Sonnet 프로모션 인트로가($2/$10)를 적용하면 T09에서 역전한다** — W-SIMPLE $3.22 < W-COMPLEX $4.07. 즉 임계의 위치(2축이 COMPLEX인가)는 모델 단가비의 함수다. 정가 환원(2026-09~) 후에는 현행 임계가 유효하나, 프로모션 기간 중에는 임계를 3축으로 올릴 여지가 생긴다. n=1 캐비앗(경계 과제 각 파이프라인 1회 실측)은 유지한다.

> `classify_complexity` 도구는 반드시 이 문서의 6축 정의·결정 규칙·편향 원칙을 그대로 따라야 한다. 축 판정 근거가 이 문서에서 확인되지 않으면 추측하지 말고 확인 불가로 답한다(G4).
