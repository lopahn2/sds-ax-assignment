# 04. 품질 평가 — 모든 파이프라인이 상한에 도달했다

평가는 PRD만 읽고 독립 작성된 100점 루브릭(기능 40 · 인증 보안 15 · 인가 10 · 견고성 10 · 코드 품질 10 · UI/UX 15)으로, 케이스별 독립 평가자가 실제 서버를 구동해 T0~T32 기능 테스트 프로토콜(회원가입→로그인→CRUD→친구 수명주기→비친구 403→재시작 영속성→악의적 입력)을 전부 실행하며 채점했다. 이후 감사 에이전트가 5건의 채점표를 교차 검증했다.

## 카테고리별 점수 (감사 확정)

|---|---|---|---|---|---|

## 유일한 확정 감점: case3 코드 품질 −2점

프런트엔드 `api.js`에 `USE_MOCK = false`로 잠긴 약 25줄의 개발용 mock 스캐폴드가 남아 있었다 — 상수 false 분기 뒤의 도달 불가능한 코드로, 루브릭의 데드 코드 기준에 저촉. 담당 평가자는 통과로 판정했지만 감사가 이를 관대 판정으로 적발해 조정했다. 다섯 앱 모두 scrypt+솔트 해싱, 서버측 세션 무효화, 원자적 파일 쓰기, 경로 탐색 방어까지 갖춘 사실상 만점 구현이었다.

## 감사(교차 검증) 결과

감사 에이전트는 5개 채점표의 산술을 전수 검증(하위 항목→카테고리→총점 합산 모두 무결)하고, 핵심 주장을 코드로 직접 스팟체크했다: 5개 구현 전부 scrypt + 사용자별 CSPRNG 솔트, 32바이트 랜덤 세션 토큰, 저장 데이터에 평문 비밀번호 없음, 순수 stdlib 의존성 확인.

체계적 패턴 2건을 식별했다.
1. "도달 불가능한 함수" 기준을 5명의 평가자 모두 "호출도 export도 없는 것"으로 일관 해석했는데, case3의 평가자만 이 관대함을 상수로 꺼진 mock 블록까지 확장 적용 → 감사가 −2 조정.
2. UI 항목은 전 평가자가 동일하게 정적 HTML/JS 리뷰 + 라이브 API 검증으로 채점(실 브라우저 미구동) — 방법이 균일해 케이스 간 공정성은 유지됨.

평가자 간 변동성 관찰: case3_1은 서로 다른 두 독립 평가에서 98점(FE 중복 −2)과 100점(동일 항목 통과)을 받았다. 감사는 루브릭 원문 기준으로 최종본을 재검토해 100점을 확정했다. **LLM 평가자의 ±2점 판정 변동은 이 벤치마크의 측정 오차 범위로 봐야 한다.**

## 해석 주의 — 천장 효과 (ceiling effect)

과제 난이도가 두 모델 모두의 역량 상한 아래에 있어 품질이 변별력을 갖지 못했다(98~100점). 각 케이스 1회 실행(n=1)인 데다, 같은 산출물에 두 평가자가 98점과 100점을 준 사례(case3_1)에서 보듯 ±2점은 평가 노이즈 범위다. **이 벤치마크의 유효한 변별 지표는 비용과 시간이다.** 더 어려운 과제에서는 품질 축이 벌어질 수 있으며, 그때는 결론이 달라질 수 있다 (실제로 라운드 2에서 확인됨 — `research/round2-results-verdicts.md` 참고).
