# 라운드 2 — 복잡 과제 (실시간 협업 칸반 TeamBoard)

라운드 1에서 다섯 파이프라인이 모두 품질 상한(98~100점)에 도달해 변별이 사라졌다. 라운드 2는 $/점 기준 상위 3개 조합만 골라 훨씬 어려운 과제로 재측정한다 — 품질에 실제로 격차를 낼 수 있는 난이도에서 "제한된 토큰으로 가장 효과적인 개발법"이라는 원질문을 다시 묻는다.

## 09. 배경과 과제 — 왜 상위 3개만, 무엇을 시켰나

라운드 1의 결론은 명확하되 반쪽이었다: 이 난이도에선 품질이 파이프라인을 가리지 못했다(감사 확정 98~100점). 변별은 오직 비용·시간이었고, "더 어려운 과제에서는 결론이 달라질 수 있다"가 R1이 남긴 미해결 질문이었다. 라운드 2는 그 질문에 답한다 — R1에서 $/점(100점당 비용) 상위 3개 조합만 승격시켜 복잡 과제로 재대결한다. 하위 2개(case2 $0.0872, case1 $0.1095)는 탈락했다.

### 승격 케이스

| 승격 케이스 | 파이프라인 | R1 $/점 | R1 순위 | 에이전트 |
|---|---|---|---|---|
| case3 | Opus 설계 → Sonnet FE+BE 병렬 | $0.0513 | 1위 | 3 |
| case2_1 | Sonnet 설계 → Opus 풀스택 | $0.0583 | 2위 | 2 |
| case3_1 | Sonnet 설계 → Opus FE+BE 병렬 | $0.0737 | 3위 | 3 |

R1 $/점 = R1 순수 개발 비용(정가) ÷ 점수(= 100점당 비용 ÷ 100). R2도 productive(정가) ÷ 점수로 동일 산출해 라운드 간 방법론을 맞췄다.

### 과제 — TeamBoard: 실시간 협업 칸반 보드

여러 사용자가 워크스페이스 단위로 모여 칸반 보드를 실시간으로 함께 편집하는 웹 앱. 규범(normative) PRD로 URL 경로·JSON 필드명·HTTP 상태코드를 정확히 고정했고, 기능 요구 44개(FR-1~44) + 비기능 7개(NFR-1~7)로 구성된다. 스택 제약은 R1과 동일 — Node.js 표준 라이브러리만, 외부 의존성 0, 단일 server.js, JSON 파일 영속성, 정적 UI 동일 서버 제공.

### 난이도 축 — R1에 없던 9가지 복잡성

- **SSE 실시간 동기화** — text/event-stream, hello 선행, 보드별 seq 엄격 증가, 20명 동시 구독 무유실, 변경→전달 <1초, Last-Event-ID 재접속 리플레이
- **낙관적 동시성** — 모든 카드 변경에 expectedVersion, 동일 버전 동시 요청은 정확히 하나만 성공(lost update 금지), 409에 현재 카드 동봉
- **4단계 역할 권한** — owner/admin/member/viewer 권한 매트릭스, 비멤버 403, admin이 admin을 못 건드림, member는 자기/담당 카드만 삭제
- **WIP 제한** — 컬럼 wipLimit 도달 시 422, 같은 컬럼 재정렬은 예외, 경쟁 조건에서 최종 카드 수 ≤ N
- **멘션·알림** — 댓글 @username 파싱, 실존 WS 멤버·비본인만, 사용자당 중복 1건; 담당 지정 시 assigned 알림
- **활동 로그** — 보드별 seq를 SSE와 공유(동일 번호), 10종 이벤트 타입, 최신순 커서 페이지네이션
- **검색·페이지네이션** — title+desc 부분일치 + assignee/label AND, 아카이브 제외, updatedAt 내림차순, cursor 방식(limit 기본 50 / 최대 200)
- **대량 데이터 성능** — 5,000 카드 시드 기준 보드 조회 p95 < 300ms, 검색 < 500ms, 카드 생성/이동 < 200ms
- **크래시 무결성** — 원자적 쓰기(temp+rename), SIGKILL 후 재부팅 클린, 손상 파일 격리, 재시작 후 세션·로그아웃 무효화 유지

## 10. 평가 방법론 — 봉인 하니스 + LLM 판정 + 감사

R1의 평가는 사람이 서버를 구동해 채점하는 방식이었다. R2는 규범 PRD의 엄밀함에 맞춰 기계 채점 가능한 86점을 자동화된 봉인 하니스로, 나머지 14점(코드 품질·UI/UX)만 LLM 판정으로 돌렸다. 개발과 평가는 완전히 격리됐다.

### 봉인 하니스 (sealed kit) — 자동 86점

하니스는 어떤 구현도 들여다보기 전에 동결됐고, 채점 시 각 케이스의 HTTP/SSE 표면과 DATA_DIR만 읽을 뿐 구현 소스는 절대 읽지 않는다. 프로브는 PRD가 규범으로 못박은 경로·필드·상태코드에만 의존한다(특정 구현에 맞춘 튜닝 금지). 64개 하위 항목이 각각 {0, ⅓, ⅔, 1} 부분점수로 채점된다.

| 키 | 카테고리 | 배점 | 항목 수 | 채점 |
|---|---|---|---|---|
| F | 기능 완성도 (FR-1~33/39/40) | 30 | 24 | 자동 |
| RT | 실시간 동기화 정합성 (SSE) | 12 | 8 | 자동 |
| CC | 동시성·트랜잭션 정확성 | 10 | 6 | 자동 |
| AZ | 인증·인가 권한 매트릭스 | 12 | 8 | 자동 |
| RB | 견고성·에러 처리 | 8 | 7 | 자동 |
| PF | 성능 (5,000 카드) | 8 | 5 | 자동 |
| IN | 데이터 무결성·영속성 | 6 | 6 | 자동 |
| | **자동 소계** | **86** | **64** | |
| CQ | 코드 품질·아키텍처 | 8 | — | LLM |
| UX | UI·UX | 6 | — | LLM |
| | **총점** | **100** | | |

### 하니스가 무른 게 아님을 증명 — 셀프테스트 스텁 19.5/86

"세 케이스가 다 86점 만점"이라는 결과가 하니스의 관대함 탓이 아님을 검증하려고, 최소 골격만 갖춘 셀프테스트 스텁 구현을 같은 하니스에 넣자 **19.5/86**에 그쳤다. 프로브는 매트릭스 전 셀이 통과할 때만 만점을 주고, 동시성은 both-200(lost update)을 0점 처리하며, 무결성은 실제 SIGKILL+재시작 사이클을 돌린다. 만점은 실제 규범 준수의 결과다.

### LLM 판정 프로토콜 — 나머지 14점

CQ(8)·UX(6)는 LLM 판정관이 채점하되, 관대화를 막는 두 장치를 걸었다.
- **강제 감점 사냥**: 판정관은 카테고리마다 감점 후보를 최소 5개 열거하고, 각각을 적용하거나 file:line 인용과 함께 기각해야 한다. 근거 없는 칭찬은 0점.
- **앵커**: "그냥 잘 만든" 구현은 60~75% 구간(CQ 4.8~6.0/8, UX 3.6~4.5/6)에 놓이도록 기준을 못박음. 만점은 모듈 경계·원자적 영속성·중앙화된 인증/에러/버전 로직·데드코드 0을 각각 인용해야만 준다.

### 감사(audit) — 조정 0건, 하니스 스팟체크 통과

감사 에이전트가 세 판정표를 교차 검증했다. 세 케이스 모두 점수 조정 0건(adjustments: []) — 판정관들이 인용 규칙과 5후보 감점 사냥을 실제로 지켰음을 확인했다. 나아가 하니스 프로브 자체를 스팟체크했다: CC-01(진짜 병렬 충돌 PATCH), CC-03(WIP 경쟁), AZ-02/AZ-08(5역할 매트릭스 + 회수/SSE 종료), IN-01~04(SIGKILL 크래시 복구·단조 seq·토큰 영속성)를 리뷰해 "프로브가 PRD 규범 동작을 진짜로 검증하며 엄격하다 — 공허한 통과(vacuous pass)는 없다"고 판정했다.
